# Future Implementations & Feature Roadmap

This document outlines unimplemented features from the `liboqs` bindings that would enhance the security, performance, and functionality of the Dart wrapper.

## 1. Security Enhancements

### Constant-Time Memory Comparison (`OQS_MEM_secure_bcmp`)
Standard Dart `ListEquality` or `==` operators are not constant-time. They exit as soon as a mismatch is found, which can leak information about the secret via timing side-channels.
- **Goal:** Implement `LibOQSUtils.secureCompare(Uint8List a, Uint8List b)`.
- **Native Function:** `int OQS_MEM_secure_bcmp(const void *a, const void *b, size_t len)`
- **Priority:** High (Critical for verifying shared secrets and MACs).

### Context-Aware Signatures (`sign_with_ctx_str`)
Standard signatures (ML-DSA, SPHINCS+, etc.) support an optional context string for domain separation.
- **Goal:** Update `Signature.sign` and `Signature.verify` to accept an optional `Uint8List? context`.
- **Native Function:** `OQS_STATUS OQS_SIG_sign_with_ctx_str(const OQS_SIG *sig, uint8_t *signature, size_t *signature_len, const uint8_t *message, size_t message_len, const char *ctx_str, size_t ctx_str_len, const uint8_t *secret_key)`
- **Priority:** Medium (Required for protocol compliance with FIPS 204/205).

## 2. Hardware & Performance

### CPU Extension Detection (`OQS_CPU_has_extension`)
Exposing hardware capability checks allows developers to verify if the native library is utilizing hardware acceleration (AES-NI, AVX2, Neon).
- **Goal:** Add `LibOQS.hasCpuExtension(String extension)`.
- **Native Function:** `int OQS_CPU_has_extension(OQS_CPU_EXT ext)`
- **Priority:** Low (Useful for debugging and performance tuning).

### Custom Randomness Providers
`liboqs` allows switching the RNG algorithm (OpenSSL, System, NIST-KAT).
- **Goal:** Fully wrap `OQS_randombytes_custom_algorithm` to allow Dart-defined callbacks for entropy.
- **Priority:** Low (Advanced use cases only).

## 3. Library Architecture

### Direct Algorithm Entry Points
The current implementation uses string-based lookups (`OQS_KEM_new`). `liboqs` also provides direct static constructors for every algorithm.
- **Goal:** Add named constructors like `KEM.ml_kem_512()` which call `OQS_KEM_ml_kem_512_new()` directly.
- **Benefit:** Slight performance gain (skips string comparison in C) and type safety.
- **Priority:** Low.

### Pre-hashed Signature Variants
Some algorithms support "Pre-hash" versions (e.g., `slh_dsa_sha2_256_prehash_sha2_128s`).
- **Goal:** Ensure these are correctly identified and supported in the `Signature` class.
- **Priority:** Medium.

## Additional Findings from Codex Review

These items were identified after comparing the generated bindings with the current Dart wrapper surface. They are intentionally separate from the Gemini-generated roadmap above.

### Deterministic KEM Encapsulation (`OQS_KEM_encaps_derand`)
The wrapper already supports deterministic keypair generation through `OQS_KEM_keypair_derand`, but the bindings also expose deterministic encapsulation and the `length_encaps_seed` metadata field.
- **Goal:** Add `KEM.encapsulateDerand(Uint8List publicKey, Uint8List seed)` plus metadata helpers such as `encapsulationSeedLength` and `supportsDeterministicEncapsulation`.
- **Native Function:** `OQS_STATUS OQS_KEM_encaps_derand(const OQS_KEM *kem, uint8_t *ciphertext, uint8_t *shared_secret, const uint8_t *public_key, const uint8_t *seed)`
- **Priority:** Medium (Useful for KATs, reproducible test vectors, and deterministic ML-KEM workflows).

### Empty Message Signing and Verification
`LibOQSUtils.uint8ListToPointer()` currently rejects empty byte arrays. Empty messages are valid inputs for signature APIs, so `Signature.sign(Uint8List(0), secretKey)` and matching verification likely fail before reaching liboqs.
- **Goal:** Allow zero-length message buffers for signature sign/verify while keeping strict validation for inputs that must not be empty, such as keys and ciphertexts.
- **Affected Area:** `Signature.sign`, `Signature.verify`, and shared pointer conversion utilities.
- **Priority:** High (Correctness issue for valid signature inputs).

### Stateful Signature APIs (`OQS_SIG_STFL_*`)
The bindings include the stateful signature API surface for XMSS/LMS-style algorithms, including algorithm listing, key creation, signing, verification, signature counters, locking hooks, and key serialization/deserialization. No Dart wrapper currently exposes this.
- **Goal:** Design a dedicated stateful signature wrapper instead of extending the stateless `Signature` class.
- **Native Functions:** `OQS_SIG_STFL_new`, `OQS_SIG_STFL_keypair`, `OQS_SIG_STFL_sign`, `OQS_SIG_STFL_verify`, `OQS_SIG_STFL_sigs_remaining`, `OQS_SIG_STFL_SECRET_KEY_serialize`, `OQS_SIG_STFL_SECRET_KEY_deserialize`, and related secret-key lifecycle functions.
- **Priority:** Medium (Large feature with important API design and key-state safety concerns).

### Public Export Completeness
`package:oqs/oqs.dart` exports `Signature` but not `SignatureKeyPair`. Users can receive the return value from `generateKeyPair()`, but cannot name the type directly from the public package import.
- **Goal:** Export `SignatureKeyPair` from `oqs.dart`, and review whether all intended public result/key classes are exported consistently.
- **Priority:** Low (API polish and usability).

### Context Support Discovery
If context-aware signatures are implemented, the wrapper should also expose `OQS_SIG_supports_ctx_str` so callers can check whether a selected algorithm supports context strings before signing.
- **Goal:** Add `Signature.supportsContextString(String algorithmName)` and/or an instance getter on `Signature`.
- **Native Function:** `bool OQS_SIG_supports_ctx_str(const char *alg_name)`
- **Priority:** Medium (Complements context-aware signing and avoids trial-and-error API usage).

### Direct Algorithm Entry Points Are Low Value
The direct static constructors in the generated bindings are available, but the current string-based `OQS_KEM_new` and `OQS_SIG_new` approach better matches liboqs runtime capability checks and build-dependent algorithm availability.
- **Recommendation:** Do not prioritize named per-algorithm constructors unless there is a strong user-facing ergonomics requirement. The performance benefit is likely negligible compared with cryptographic operation costs.
- **Priority:** Low.
